# Architecture

Module 01 establishes a browser application, an API gateway, and local platform dependencies. The web app calls the gateway over HTTP. The gateway provides liveness and readiness and owns centralized configuration, structured request logging, correlation IDs, CORS, and the base error envelope.

PostgreSQL/PostGIS is the future transactional and geospatial store; Redis is available for later caching; Neo4j for the future city knowledge graph; Qdrant for later vector search; Redpanda provides a Kafka-compatible event fabric; and MinIO supplies local S3-compatible storage. Module 01 deliberately does not put domain data or fake workflows into these systems.

Every service gets its own **database** on the one shared Postgres instance, not just its own tables (`infrastructure/postgres/init-databases.sql`, applied once when the `postgres_data` volume first initializes). This was tried the other way first -- one `cityos` database for everything -- and reverted after it broke in practice: three independent Alembic histories writing into one shared `alembic_version` table collide the moment their revision IDs diverge, so the second and third service to migrate fail with "Can't locate revision" against a version id that belongs to a different service's history entirely.

Module 02 adds the platform's first downstream service, `identity`, and establishes the pattern every later service follows: its own FastAPI app, its own Alembic history, its own Postgres tables, and its own test suite, fronted by the gateway rather than called directly. The gateway forwards `/api/v1/auth`, `/api/v1/users`, `/api/v1/roles`, `/api/v1/departments`, and `/api/v1/permissions` to `identity` verbatim (method, headers, query string, body, and redirects) via `app/api/proxy.py`; it does not decode tokens or make authorization decisions itself. `identity` owns:

- Registration, login, logout, email verification (logged, not sent -- see its README), and password reset
- Short-lived JWT access tokens (15 min) carrying a resolved permission list, and longer-lived rotating opaque refresh tokens (7 days) -- authorization elsewhere is a JWT decode, not a database round trip
- Google and GitHub OAuth (authorization-code flow)
- RBAC: Users, Roles, Departments, and Permissions, seeded from `app/db/seed_data.py` (Alembic `0002`) with the roles and permission examples from the platform spec

Module 03 adds the platform's second downstream service, `city-core`, following the same pattern. The gateway forwards `/api/v1/roads`, `/api/v1/hospitals`, `/api/v1/vehicles`, and `/api/v1/incidents` to it the same way it forwards identity's routes -- `app/api/proxy.py`'s `_SERVICES` map is now two entries, and a third module adds a third. `city-core` owns Roads, Hospitals, Vehicles, and Incidents (the entities the spec's own worked examples revolve around); it has no users of its own and never issues tokens, so it verifies the JWTs `identity` issued using the same shared `JWT_SECRET` rather than calling back to identity or duplicating its user database. The incident lifecycle (`DETECTED -> VERIFIED -> ASSIGNED -> RESPONDING -> RESOLVED -> ANALYZED`, spec section 16) is enforced server-side in `app/services/incidents.py`, not left to callers. Geography is intentionally a placeholder here -- plain lat/lon columns and a JSON waypoint list, not PostGIS geometry -- so the schema stays identical on SQLite (unit tests) and PostgreSQL; see `services/city-core/README.md` for when that should change.

Every other directory under `services`, `data-providers`, `packages`, and `ml` remains reserved for future modules and is not a deployable service today. Shared contracts and validation live in `packages/types` and `packages/validation` (TypeScript interfaces and Zod schemas mirroring identity's Pydantic schemas by hand), consumed by `apps/web`'s login/register/account pages.

`data-providers/traffic` and `data-providers/vehicles` are the exception: real, complete synthetic data services (spec section 28) wired into the rest of the platform via Redpanda -- see `services/city-core/README.md`'s "Live data pipeline" section for the full path from a provider's tick to a live update in the browser. `data-providers/hospitals`/`weather`/`energy`/`water`/`incidents` are not; `hospitals` has a `main.py` but no `pyproject.toml`, and the rest are empty.
